# 对抗性安全测试（Red Team）

这一组脚本不是「跑通 happy path」的功能测试，而是**主动攻击自己的实现**，用来证明
README 里那些安全宣称不是自说自话。功能测试在 `../tests/`（pytest，74 个用例），
这里是它们的补充：**假设攻击者存在**。

结论先给：**8 项宣称全部经攻击验证属实**，另有 1 处健壮性缺口（见文末）。

## 怎么跑

全部从项目根目录运行（脚本内部用 `sys.path.insert(0, ".")` 找 `app/` 包）：

```bash
cd secure_file_transfer
./.venv/Scripts/python.exe security_tests/run_A_crypto.py
```

| 脚本 | 攻击目标 | 预计执行时间 | 磁盘占用 |
|---|---|---|---|
| `run_A_crypto.py` | 加密层篡改检测 | < 1 秒 | 0 |
| `run_B_resume_traffic.py` | 断点续传是否真省流量 | ~5 秒 | ~1 MB |
| `run_C_kill_resume.py` | 断开进程后能否真的续传 | ~30 秒 | **~150 MB** |
| `run_D_memory.py` | 大文件内存是否恒定 | ~20 秒 | **~150 MB** |
| `run_E_robustness.py` | 服务端抗攻击能力 | ~15 秒 | ~1 MB |
| `run_replay.py` | 认证重放攻击 | ~5 秒 | ~1 MB |

C 和 D 会生成 50 MB 测试文件；跑完可以手工删掉 `security_tests/*.bin` 与
`security_tests/srvdata*/`、`security_tests/recv_*/`。数据不入库（见 `.gitignore`）。

## 各脚本攻击什么

### A —— 加密层（`run_A_crypto.py`）
逐个制造 8 类密文破坏，断言**全部**被 GCM 拒绝而不是返回垃圾明文：

- 翻转密文任意 1 bit ／ 翻转认证标签 ／ 截断密文
- 交换两个数据块的密文（验证 AAD 把 `file_id + offset` 绑进了认证标签，块不可跨位搬移）
- 用错误密钥解密 ／ 用错误 AAD 解密
- 传 16 字节密钥（应当拒绝——这是「真的是 AES-**256** 而不是 128」的直接证据）

**实测：8/8 全部抛 `ValueError`。** 这就是 CBC 做不到的事：CBC 只保保密性，
密文被改一个 bit 只会解出乱码而不报错；GCM 是 AEAD，篡改立刻暴露。

### B —— 断点续传是否真省流量（`run_B_resume_traffic.py`）
不信任服务端自己的说法。在客户端与服务端之间**插一个 TCP 代理，独立统计
客户端→服务端方向的原始字节数**。造 5 块（320 KiB）文件，先伪造「已收 2 块」的现场。

**实测：线上仅 197239 字节，而整文件传输需要约 328407 字节。** 服务端协商偏移
`resumed_from == 2 × 65536`。如果实现是「假装续传、实际重传」，这个数字会接近整文件。

### C —— 强制中断后能不能恢复（`run_C_kill_resume.py`）
作者原来没测这个场景。传 50 MB 到一半**直接杀掉客户端进程**（不是优雅关闭），
断言服务端留下 `.part` + `.part.meta.json`；再起客户端重传同一文件。

**实测：第二次只发了 25.8 MB（整文件 52.5 MB），最终逐字节一致，完成后无残骸。**
这条证明了 `.part` + 元数据是真正跨会话持久化的，不是内存里的假象。

### D —— 内存是否真的恒定（`run_D_memory.py`）
用 `tracemalloc` 分别测量接收 5 MB 与 50 MB 文件的**峰值内存增量**。若实现里还有
任何一处 `f.read()` 全量读，峰值会随文件大小线性增长。

**实测：5 MB → 峰值 1281 KiB；50 MB → 峰值 806 KiB。** 文件大小差 10 倍，峰值反而更小，
说明内存占用与文件大小无关，64 KiB 流式是真的。

### E —— 服务端健壮性（`run_E_robustness.py`）
五个子攻击：

| 编号 | 攻击 | 期望 |
|---|---|---|
| E1 | 不发 HELLO 直接发乱码／畸形帧 | 服务端不崩，其它客户端仍可用 |
| E2 | 半开连接（连上不发数据） | 不阻塞其它连接 |
| E3 | 4 个客户端并发上传不同文件 | 4 个文件都逐字节正确，不串包 |
| E4 | 文件名攻击 `../../../etc/passwd`、`..\..\windows\win.ini`、绝对路径、空名 | 全部拒绝，`share_dir` 外不产生任何文件 |
| E5 | 帧头声明 `payload_len = 2 GB` | 抛 `ProtocolError`，不尝试分配内存 |

### 重放攻击（`run_replay.py`）
抓一次合法的 AUTH 帧，在新会话里**原样重放**，断言服务端拒绝。

**实测：重放 → `AUTH_FAIL`；同会话内正确应答 → `AUTH_OK`。** 因为服务端每次连接都
发新的随机盐 + 随机挑战数，且口令本身从不过网（客户端只回 `HMAC(主密钥, 挑战数)`）。

## 仍然存在的健壮性缺口（已知、未修）

- **连接数治理**：服务端每个连接起一个线程。E2 证明半开连接不会阻塞**其它**
  连接，但没有最大连接数上限与空闲超时，理论上可被连接耗尽拖垮。
  `ServerConfig` 已预留 `max_clients` / `conn_timeout` 字段。
- **同目标并发**：两个客户端同时上传**同一份内容**时，历史实现会在
  `os.replace` 上撞 Windows 文件锁（`WinError 32`）。现已通过
  「按目标文件串行化会话 + 内容寻址幂等短路」解决：后到的会话发现成品已就位，
  零流量成功。可用 6 并发同文件复测（见 `../verify_resume.py` 的思路自行构造）。
- **跨进程部署**：`ResumeStore` 的锁是**进程内**的。多进程/多机部署需换成文件锁
  （`filelock` / `fcntl.flock`）或外部协调。
